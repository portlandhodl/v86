# TODOs: x86-64 (long mode) in v86_64

This is the roadmap for v86_64, the 64-bit fork of v86, written so that an
engineer (human or LLM) with no prior context can pick it up. It covers how
the code is laid out, the open work, the design of the 64-bit parts and the
lessons learned. The history of individual bug fixes is in `git log`.

**Status (2026-10).** Alpine 3.19 x86_64 boots from its ISO (SeaBIOS +
ISOLINUX) to an interactive root shell in about 30 s, with 64-bit code
running in the JIT (`tests/longmode/alpine.js`). 32-bit userspace runs on the
64-bit kernel in compatibility mode (`tests/api/compat32.js`). No
unimplemented instructions remain in the advertised feature set, and every
CPU-relevant kvm-unit-test passes. Guest RAM can be up to 16 GiB with the
mem64 build. Milestones M1–M4 are done. Current work is graphical
distributions (M5, §3.1). All work lands on `master`.

| Milestone | State |
|---|---|
| M1: long-mode CPU core (REX, 64-bit registers and addressing, 4-level paging) | Done |
| M2: 64-bit kernel to userspace (interrupts, syscall, NX, 48-bit addresses) | Done |

## 0. Orientation

- The CPU core is Rust compiled to WebAssembly (`src/rust/`, crate root
  `src/rust/lib.rs`). Devices and glue are JavaScript (`src/*.js`,
  `src/browser/`).
- Two execution engines share one instruction table (`gen/x86_table.js`):
  - **Interpreter.** `gen/generate_interpreter.js` generates
    `src/rust/gen/interpreter{,0f}.rs` (gitignored, regenerated by make): a
    big `match` that calls the hand-written `instr*` functions in
    `src/rust/cpu/instructions.rs`, `instructions_0f.rs`,
    `instructions_64.rs` and `instructions_0f38_0f3a.rs`. Dispatch is on
    `opcode | size << 8`, with size 0 = 16-bit, 1 = 32-bit and 2 = 64-bit.
  - **JIT.** `src/rust/jit.rs` + `codegen.rs` + `jit_instructions.rs`
    compile hot guest pages to wasm modules at runtime. 64-bit code has its
    own tables (`gen/generate_jit64.js` → `src/rust/gen/jit64*.rs`, design in
    the header comment of `src/rust/jit64.rs`). Entries are cached per page
    in `tlb_code` / `tlb_code_high`, keyed by `CachedStateFlags`, which
    includes the mode (`is_64` is bit 4).
- CPU state is a fixed-offset map in wasm linear memory, defined in
  `src/rust/cpu/global_pointers.rs` and mirrored by views in `src/cpu.js`
  (the constructor and `get_state`/`set_state`). **A new state field must be
  added on both sides.**
- Registers are 16 × u64. The 8/16/32-bit views alias the low bytes, and
  32-bit writes zero-extend. `prefixes` is a u16 that carries the REX bits
  (`prefix::PREFIX_REX_{W,R,X,B,PRESENT}`).
- 64-bit lazy flags use `OPSIZE_64` and separate u64 slots
  (`last_op1_64`/`last_result_64`). The 32-bit paths are unchanged.
- Hitting an `unimplemented!()` aborts the VM with a loud message. That's
  deliberate, so bring-up failures are easy to spot.

## 1. Build and test

```sh
make build/v86-debug.wasm          # debug wasm (fast enough, has dbg_asserts)
make build/v86.wasm                # release wasm
make build/v86-mem64-debug.wasm    # mem64 build (guest RAM > 3 GiB)
make nasmtests                     # 32-bit instruction tests vs the host CPU via gdb
make nasmtests-force-jit           # the same, forcing JIT compilation
make longmode-tests                # 64-bit tests: interpreter, JIT_THRESHOLD=1, no chaining,
                                   # ELF64 multiboot, self-IPI
make rust-test expect-tests
make tests                         # guest boots (images: see Readme)
node tests/kvm-unit-tests/run.mjs tests/kvm-unit-tests/x86/<t>.flat
```

- nasmtests and longmode-tests need nasm and gdb. Without root access, run
  `apt-get download nasm && dpkg-deb -x nasm_*.deb .` and put the extracted
  `usr/bin` on PATH.
- The x86_64 kvm-unit-tests build from `tests/kvm-unit-tests/`
  (`./configure --arch=x86_64 && make`). These pass: access, apic, debug,
  eventinj, idt_test, ioapic, memory, msr, pcid, port80, realmode, setjmp,
  sieve, smptest, syscall, xsave. Not applicable to v86: emulator, asyncpf,
  svm/vmx/pmu/hyperv/intel-iommu/s3, and the tsc tests.
- Distribution boots: `ALPINE_ISO=... tests/longmode/alpine.js` (or
  `ALPINE_KERNEL`/`ALPINE_INITRD`), `tests/api/compat32.js`, and
  `tests/api/high-mem.js` for RAM above 4 GiB.
- On the mem64 build, also run
  `V86_WASM_PATH=build/v86-mem64-debug.wasm MEMORY_MB=3072 node tests/api/2g-mem.js`
  (see §5).
- Not run regularly: `jitpagingtests` (hangs at baseline) and `qemutests`
  (need a QEMU install).

**The golden rule: 32-bit behaviour must stay bit-identical.** Run the full
nasm suite, both variants, after every non-trivial change.

## 2. How to add a 64-bit instruction

1. If the opcode has `os: 1` in `gen/x86_table.js`, the generator already
   emits a `0x2xx` case that calls `instructions::instr64_*` or
   `instructions_0f::instr64_*` (glob re-exported from `instructions_64.rs`).
   Opcodes without `os` share one body for all sizes; if REX matters (e.g.
   0x90, 0x63, bswap), make that body check `*is_64`/`rex_w()`/`rex_b()`.
2. Write the body in `instructions_64.rs` using the existing idioms:
   `read_reg64`/`write_reg64`, `safe_read64s`/`safe_write64`/
   `safe_read_write64`, the arith helpers in `arith.rs` (`add64` etc.), and
   sign-extended imm32 (`imm as i64 as u64`). `rex_b()`/`rex_r()` are already
   folded into the generated register indices.
3. Opcodes that default to 64-bit operands in long mode need `d64: 1` in the
   table (see push/pop/call/ret). Group 0xFF mixes default-64 sub-ops
   (call/jmp/push) with REX.W-gated ones (inc/dec), so inc/dec re-check
   `rex_w()` and fall back to the 32-bit body.
4. Opcodes with an embedded register (B8+r etc.) need `rex_b()`.
5. Instructions that hardcode AH–BH must bypass the REX remap via
   `read_reg8_legacy_high`/`write_reg8_legacy_high`.
6. For native JIT code, add it to `gen/generate_jit64.js`. Otherwise the
   instruction is compiled as a call of a generated wrapper around the
   interpreter handler, which is correct but slower.
7. Add a check to `tests/longmode/longmode.asm` (store a qword at
   `[r15 + N*8]` and add the expected value in `run.js`).

## 3. Open work

### 3.1 M5: graphical distributions

Debian testing (live Xfce) and Ubuntu 26.04 Desktop have profiles in
`profiles/`, and Xubuntu 24.04 has `examples/xubuntu.html`. The CPU surface is believed
complete, so the job is finding behavioural bugs, not missing instructions.
Bring guests up the way Alpine was brought up: serial console first
(`console=ttyS0`), then the desktop.

What's available:
- **Display.** QEMU/Bochs stdvga (PCI 1234:1111, DISPI at ports
  0x1CE/0x1CF, LFB at 0xE0000000). Linux's `bochs` DRM driver binds to it.
  There's also a 2D virtio-gpu. There's no 3D, so OpenGL goes through
  llvmpipe/softpipe.
- **Input.** PS/2 keyboard and mouse, plus virtio.
- **CPU.** x86-64-v1 plus SSE3/SSSE3/SSE4.1/SSE4.2/POPCNT/RDRAND. CX16 isn't
  advertised, and there's no AVX.

Tasks:
- Boot the Ubuntu Server and Desktop live ISOs (cdrom with `async: true`) to
  a shell, then to a desktop. systemd and snapd will take minutes.
- Use a light X11 session (Xfce, LXQt, i3) on the modesetting driver before
  trying GNOME Shell, which needs GL.
- `vga_memory_size` defaults to 8 MiB. 1920x1080x32 needs 16–32 MiB.
- Optional: the bochs-display variant (revision 2, MMIO BAR for DISPI) to
  avoid io port exits.

### 3.2 JIT performance (M4 follow-ups)

`tests/benchmark/bench64.js` runs the same workload in 32-bit and
higher-half 64-bit mode. Rough numbers: 32-bit JIT ~1100–1200 MIPS, 64-bit
interpreted ~80, 64-bit JIT ~620–685. On an Alpine boot (~6G instructions),
host time splits into ~55% jitted code, ~13% interpreter (3% of
instructions, at ~10× the cost each), ~8% main loop and dispatch, ~4%
wrappers and ~2.5% compilation. Bigger modules and lower hotness thresholds
were both measured slower, because compile time dominates.

- **Generated code size.** A 64-bit memory access is ~40 wasm instructions
  inline (~15 on a data-TLB-cache hit). Smaller code means cheaper
  compilation, which would allow a lower hotness threshold. One idea: one
  shared slow-path call per module.
- **Cross-block flag liveness.** Deferred lazy flags are per block. A
  block-end commit is dead when the next block overwrites the flags before
  reading them, which needs join-point-aware liveness. imul's cf/of isn't
  deferred either.
- **Remaining interpreter calls**: 8/16-bit shifts, mul/div, cli, rep
  movs/stos (could become memory.copy/fill within a page), popf, SSE moves,
  mov cr, rdtsc.
- Inline flags for 8/16-bit operations (conditions on them still call out).
- Code in the last 16 bytes of a page always runs interpreted.
- A second data-TLB-cache entry, for blocks that alternate between the stack
  and one data page.
- A paging-structure cache, to make TLB misses cheaper.
- Release wasm size went from 2.3 to 2.95 MB because of the 2293 exported
  `jit64_*` wrappers. One dispatcher per wrapper signature would shrink it.

### 3.3 Memory above 4 GiB

- **Saved state above 2 GiB (not started).** Needs pack/unpack_memory
  chunking, a wider header than state.js's Int32, `cr3_high` and high
  memory in the state, and a STATE_VERSION bump.
- Tests: a longmode asm test with page tables and code above 4 GiB (needs a
  config over 3 GiB in `tests/longmode`), the multiboot memory map's high
  entry, kvm-unit-tests at 6 GiB, Ubuntu with 8 GiB, and a 32-bit PAE guest
  with RAM above 4 GiB.
- expect-tests and verify-wasmgen-dummy-output against the mem64 build
  (wabt needs memory64 and multi-memory enabled).

### 3.4 CPU accuracy gaps

Nothing known hits these.

- References through SS with a non-canonical address raise #GP(0) instead
  of #SS(0).
- Aligned SSE moves (`movaps`/`movapd`/`movdqa`, `movnt*`) don't #GP on
  unaligned addresses (marked `XXX`).
- SSE conversions ignore the MXCSR rounding mode and never raise the
  precision exception.
- x87 BCD (fbld/fbstp, 0xDF /4 /6) and the denormal flag are unimplemented.
- rdpmc always #UDs (it should work with CR4.PCE).
- Leaving long mode (clearing PG with LMA set) is only partly handled in
  `set_cr0`. Real kernels may do this on kexec or panic.
- Compat mode: a 32-bit-operand iret pops a legacy frame instead of an
  IA-32e frame, 64-bit (REX.W) sysexit isn't implemented, and the TF-preempt
  check in `jit_run_interpreted` only looks at the second opcode byte within
  the same page.
- Debug registers: 32-bit addresses only. No I/O breakpoints (CR4.DE), no
  general detect, and the MOV SS/POP SS/STI trap shadow isn't modelled.
- init.flat: the BIOS warm-resume vector only fires on the INIT path,
  because `reboot_internal`'s `load_bios()` wipes SeaBIOS's HaveRunPost. A
  fix needs PAM shadow-ROM registers.
- Not implemented, and fine as long as no guest needs them: 1 GiB pages,
  x2APIC (EXTD raises #GP), HPET, rdfsbase/wrfsbase, monitor/mwait, invpcid,
  a 64-bit bzImage entry point, and non-transitional virtio-pci.

## 4. Design notes

### 4.1 Addresses and the TLB

- RIP, linear addresses, segment bases, GDTR/IDTR and CR2 are 64-bit.
  Physical addresses are u64 in Rust (52-bit entry masks). CPUID 0x80000008
  reports 48 linear and 36 physical bits (`PHYSICAL_ADDRESS_BITS`), and
  `PAE_ENTRY_RSVD` follows it.
- The TLB is a flat array for pages below 4 GiB (shared with the 32-bit JIT)
  plus a direct-mapped table for high pages. `tlb_high_tag` stores the page
  number of the canonical address, and lookups use `address as i64 >> 12`,
  so non-canonical addresses never match and `do_page_walk` raises #GP(0).
- JS-facing exports keep u32 wrappers. 64-bit physical addresses cross into
  JS as f64 (`*_phys64`, `cpu.phys_to_offset`).

### 4.2 JIT64

- Block finding, control-flow structuring and module generation are shared
  with the 32-bit JIT. 64-bit code has its own generated tables, so the
  32-bit JIT's output doesn't change.
- Registers live in 16 i64 wasm locals and are spilled around interpreter
  calls and at exits. Instructions without native code are calls of
  pre-decoded `jit64_*` wrappers that return `JIT64_EXIT` when the module has
  to be left.
- Module chaining: modules take the registers as arguments and continue
  through a wasm tail call to the next entry.
- Deferred lazy flags keep last_op1/last_result in function-wide locals and
  commit at observation points: block ends, interpreter calls, and cold
  commits on memory slow paths.
- The data TLB cache keeps the last validated page in two locals. It's
  zeroed at interpreter calls, the only places where mappings can change.
- Switches: `set_jit_config(4, 1)` disables JIT64, `(5, n)` sets the hotness
  threshold (`JIT_THRESHOLD`), `(7, 0)` disables chaining
  (`JIT64_CHAINING=0`), `(8, 0)` restores eager flag stores
  (`JIT64_DEFER_FLAGS=0`), and `(9, 0)` disables the data TLB cache
  (`JIT64_TLB_CACHE=0`). Setting `NATIVE64_SKIP=group,...` at generation time
  falls back to the interpreter for groups of native instructions, which
  helps when bisecting a miscompilation.
- While debug registers or TF are armed, the CPU runs interpreter-only.

### 4.3 mem64 build (guest RAM > 3 GiB)

- `v86.wasm` handles guests up to 3 GiB. `v86-mem64.wasm` (cargo feature
  `mem64`) is loaded by starter.js when `memory_size` exceeds
  `MAX_LOW_MEMORY_SIZE`, or it can be selected with `V86_WASM_PATH`. Guest
  RAM is a separate 64-bit memory (index 1, exported as `guest_memory`), up
  to 16 GiB. CPU state, TLBs and the JIT stay in memory 0.
- Rust can't address a second memory, so all guest-RAM accesses go through
  `src/rust/cpu/guest.rs`. In the mem64 build those are placeholder exports
  (`v86_guest_*`) whose bodies `tools/patch-mem64.mjs` replaces after
  linking. V8 rejects `memory.copy` between memories of different index
  types, so cross-memory copies are loops.
- Layout (as in QEMU): low RAM is `[0, min(size, 3 GiB))` and the rest sits
  at `0x1_0000_0000` (`high_memory_size`). `phys_to_host`/`host_to_phys` must
  be a **bijection on all physical addresses**, not only RAM, because TLB
  entries encode the host address of MMIO pages too. The hole
  `[memory_size, 4 GiB)` maps to `phys + 2^40`.
- `tlb_data` entries are i64 under mem64. JIT slow paths return a status and
  stash the entry in `cpu::jit_slow_path_entry`, and the fast path must keep
  its own entry (see §5).

## 5. Hard-won lessons (read before touching decode, paging or the JIT)

- **REX bit order.** The low nibble is [W,R,X,B] in bits 3..0, so stored
  `<< 8` that's W=0x800 … B=0x100. Getting it backwards swaps W and B and
  produces very confusing mis-decodes. See `src/rust/prefix.rs`.
- **Default sizes in long mode**: operand size 32 (not 16), address size 64.
  `is_32` is false in 64-bit mode, so `is_osize_32()`/`is_asize_32()`
  special-case `is_64`, and the initial fetch in `jit_run_interpreted` has an
  explicit `is_64` branch.
- **RIP-relative addressing is relative to the end of the whole
  instruction**, immediates included (`modrm_resolve` takes `imm_len`). Test
  with `mov [rel x], r64` plus an imm32.
- **A legacy prefix after REX cancels it.** With several REX prefixes, the
  last one wins.
- **SIB index 4 with REX.X is r12, not "no index".** Dropping it silently
  corrupted Linux's identity maps.
- **Anything that re-dispatches** (the STI shadow, single-steps) must use the
  64-bit dispatch in long mode, or the next instruction decodes as 32-bit.
- **64-bit exception frames always have five slots**, and IRETQ always pops
  RSP. Exceptions key on EFER.LMA, not CS.L, so compat mode takes the
  long-mode path.
- **CPUID 0x80000008's field order matters.** Linux takes `x86_virt_bits`
  from eax[15:8]. With the fields swapped, every kernel address failed the
  canonical check, which showed up as `xxx` mount points and failed logins.
- **The mem64 stale-stash trap.** Under mem64, an identity-mapped page's
  pointer `(host_base ^ addr) & ~0xFFF` is 0, so a stale stashed TLB entry is
  usually "right" by accident. A JIT bug that used the stash on the fast path
  passed nasm and longmode tests and only broke in the kernel decompressor.
  Always run 2g-mem on mem64.
- **Check the guest before blaming the emulator.** A 100× slowdown past
  2 GiB turned out to be 32-bit Lua's GC debt counter overflowing. It
  reproduced with the JIT disabled, and every profiler counter was flat.
  (The non-profiler build's `jit_get_*` counters return 0.)
- `get_instruction_counter` is u32 and wraps on long runs.
- Debugging bring-up crashes: enable `config::LOG_PAGE_FAULTS`, use
  `emulator.cpu_exception_hook`, and don't trust the panic-time register dump
  from JS if the fault happened mid-delivery (IP has already been
  rewritten). Trust CR2 and the log sequence. `dbg_log!` formats eagerly, so
  keep hot-path traces behind a config flag.
- nasm: 16-bit absolute addresses wrap at 64 KiB (use `a32` for labels above
  64K), and far jumps from 16-bit to 32/64-bit code need an explicit `o32`.

## 6. Definition of done

Met for the CPU core: `make tests`, `make nasmtests` (+ force-jit),
`make longmode-tests` and the CPU-relevant kvm-unit-tests all pass; a modern
64-bit Linux ISO boots to a shell over serial with the JIT at interactive
speed; and 32-bit userspace runs on it.

Remaining headline work: graphical distributions (§3.1), saved state above
2 GiB (§3.3), and the accuracy gaps (§3.4).
